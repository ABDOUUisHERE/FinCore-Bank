# Account and Payment administrative read audit — Phase 8 lot 9

This lot extends durable read receipts to `/api/v1/admin/accounts/{reference}` and `/api/v1/admin/transactions/{reference}`. Existing ADMIN GET permissions remain independently enforced by Gateway and each owner. Other methods on these single-segment paths are categorized and denied as before. Root/list, extra suffixes, customer-owned APIs, internal support routes and early servlet/Gateway rejections remain outside this registry.

The registry retains ACCOUNT_INSPECT or PAYMENT_INSPECT, optional canonical resource UUID, GET/POST/OTHER method, HTTP status, finite outcome, bounded technical correlation and a safe verified JWT subject or UNAVAILABLE provenance. No amount, query/cursor, reference text, profile, response body, token or instruction is retained. The original payment actor/account owner is not the current administrator. Central actor provenance remains the producing owner's assertion.

A shared Java module buffers each bounded synchronous response and commits a separate append-only owner receipt before copying its body. Receipt storage failure replaces either success or denial with sanitized `503 AUDIT_UNAVAILABLE`. The receipt's transaction is independent of a Payment read-only snapshot or any caller rollback. Broker/central outages leave its immutable outbox source available for asynchronous retry. RESPONSE_READY describes a prepared authorized response, never transport delivery or an authoritative Ledger snapshot; Account can return 200 with Ledger UNAVAILABLE without asserting an effective status.

Account migration V3 and Payment V5 add immutable receipt tables and union their version-1 access events into the existing publisher view. Existing domain envelope and acknowledged delivery bytes must remain unchanged. Customer keeps migration V4 and its event shape while adopting the same shared response/transaction mechanism. Each domain retains its existing producer prefix; no new credential or broad financial authority is introduced.

Acceptance requires restricted-role immutability, byte-preserving upgrades, independent transaction/rollback behavior, actual lost-ack replay, signed HTTP identity/denial/failure tests, central cross-domain projection rejection, actual broker delivery/quarantine and restored receipt-storage recovery. Hosted PKCE must connect both successful reads to their retained current-staff facts, preserve Payment cursor semantics and Account's observed/unavailable distinction, and regress Customer plus scoped Account/Payment/Customer support. Actual results are recorded after execution; this contract does not accept the whole phase or platform security audit.
