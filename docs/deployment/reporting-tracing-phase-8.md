The bounded acceptance flow is hosted PKCE finance reconciliation through Gateway, Reporting and Ledger, followed by the committed Reporting access receipt, delayed outbox publication and Audit consumption. The stored trace graph must prove parent relationships, including publication after the HTTP request has ended. Kafka bodies, immutable source envelopes and their digests must remain unchanged. Retries create distinct attempt spans under the original request context.

Tracing accepts only a single strict W3C version-00 traceparent with nonzero IDs. These IDs are untrusted diagnostic context, never identity or authorization. No baggage, tracestate, raw URLs/query strings, names, resource/subject IDs, headers, credentials, financial contents or exception messages enter spans. Names and attribute keys/values are closed. New local roots are sampled; an incoming unsampled parent remains unsampled.

Only Gateway, Reporting, Ledger and Audit enable collection in this lot. Other owners keep their existing behavior. Only new Reporting receipts retain an origin context; existing deliveries have no fabricated origin. Context is delivery metadata, separate from immutable business/audit envelopes. Collector export uses a bounded asynchronous queue with a short timeout; collection is best effort and is not an audit durability guarantee. Collector outage must leave the business request and retained receipt working; dropped exports are not promised for later recovery.

## Operation and preservation

Jaeger 2.23.0 accepts OTLP/HTTP only on the private Compose network. Its query/UI endpoint is bound to `127.0.0.1:16686`; use `/api/v3/services` and `/api/v3/traces/{traceId}?rawTraces=true` for graph verification. Raw queries preserve the stored graph before Jaeger's UI clock-skew adjuster adds synthetic `@jaeger@warnings` attributes for asynchronous spans; these warnings are not attributes emitted by FinCore. The local memory store retains at most 10,000 traces and resets when Jaeger restarts. It is a development collector, with no persistent retention or production availability acceptance. Jaeger's own trace exporter is disabled. The Java SDK has a 512-span queue, 64-span export batches, 250 ms scheduling and a one-second export timeout.

`TRACING_ENABLED=true` enables only the four supported application names. Reporting also opts into reading and writing the new delivery-origin column. Apply Reporting V3 before replacing its running image: it adds nullable `event_delivery.traceparent` plus validation and an update guard for the origin and event ID. It does not rewrite source envelopes, original delivery fields, financial rows or old receipt data, and it never backfills origin context. The current receipt's context is inserted in the same independent receipt transaction; an unavailable local origin write rolls that receipt back and withholds the response under the existing audit failure policy. Collector export does not join that transaction.

For an existing installation, build `reporting-service`, `ledger-service`, `audit-service` and `api-gateway`; pause Reporting and snapshot the original rows/envelopes/delivery fields and configuration hashes; run `docker compose run --rm --no-deps reporting-migrations`; verify V3 and preservation before starting those four images with `docker compose up -d --no-deps --wait`. Start Jaeger with `docker compose up -d --no-deps jaeger`. Preserve the database, Kafka, realm and configuration volumes and all credentials. No broker identity, ACL or financial schema change is required.

The hosted-PKCE test pauses Reporting publication by temporarily revoking SELECT on its source view, waits until the HTTP span is actually stored, then restores the privilege. This proves publication after the request ended. Its finally hooks restore the privilege and any stopped Ledger/Jaeger container. The same journey verifies actual Kafka/Audit parentage and the exact retained envelope digest, collector outage with successful HTTP/central retention, and a collected Ledger failure followed by recovery. After collector restart it first requires a newly stored complete application graph: query API readiness alone does not establish exporter recovery, and polling a lost best-effort batch cannot recover it. Run it with `npx playwright test tests/e2e/tracing.spec.ts` after installing Chromium. No request deadline, role or financial assertion is relaxed.

Acceptance requires malformed/duplicate context isolation, delayed/retried publication with identical body bytes, central consume parentage, real stored graph assertions, collector outage/recovery and redaction checks. A trace header or dependency declaration alone is not proof of collection. The six required dashboards and remaining security/audit coverage retain their separate gates.

The specified Jaeger backend receives OTLP/HTTP spans and provides the local stored-graph query API. Implementation references: [OpenTelemetry SDK](https://opentelemetry.io/docs/languages/java/sdk/), [Jaeger configuration](https://www.jaegertracing.io/docs/2.dev/deployment/configuration/).
