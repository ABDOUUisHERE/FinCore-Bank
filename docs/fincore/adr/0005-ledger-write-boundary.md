# ADR 0005 — Restricted SQL ledger write boundary

Status: accepted, 2026-10-22. Implements the approved Phase 2 financial kernel.

The ledger uses a dedicated database, migration owner and runtime login. Runtime can SELECT ledger facts and execute three SECURITY DEFINER functions: provision a zero-balance account, version a guard, and atomically post a financial command. It cannot perform table DML, DDL, TRUNCATE or disable triggers. All functions fix their search path to `pg_catalog,ledger,pg_temp`; PUBLIC receives no function execution rights. A database administrator remains a privileged infrastructure actor.

The initial business chart admits exactly two distinct accounts and one currency per command. Deposits debit a synthetic settlement asset and credit a customer liability; transfers debit/credit customer liabilities; withdrawals credit settlement; merchant payments credit merchant liabilities. Full reversals invert exactly the original journal, require the original issuer, and cannot reverse a reversal. Both sides must be active, and no resulting aggregate may be negative. A synthetic deposit is capped at 1,000,000.00 per command; this is a demo control, not a complete risk/velocity policy.

Use transaction-scoped advisory locks only to serialize the transport key and durable issuer/business reference. Their sorted lock keys avoid identity-lock cycles. Hash collisions may serialize unrelated identities but cannot change their durable unique constraints or fingerprints. Account and balance rows, including restriction state, are locked in ascending account UUID order before funds/entitlement checks. The database locks provide serialization across service processes. A reversal locks its original journal before account rows. No external service call runs in the financial transaction.

The SQL function normalizes decimal strings, sorted postings and account UUIDs before hashing the command, actor, kind, reference, currency and reversal link. Definitive success and business rejection are immutable. A new transport key for the same business reference aliases the original outcome. Changed payloads conflict. Invalid syntax/chart/currency is rejected without consuming the identity. Keys and outcomes have no financial expiry. Lock timeouts ask the caller to retry/lookup the same identity; a caller must also do that after an ambiguous network failure.

A journal is unsealed only inside its creating transaction. Posting insertion requires that transaction and an open journal. Only sealing is an allowed journal update. Deferred constraints verify every journal, including an empty one, has matching debit/credit sums and a matching total. Committed journals, postings, outcomes, keys and outbox facts reject mutation and truncation. A deferred outcome constraint links POSTED results to their journal and REJECTED results to no journal. Aggregate balance and per-account-version outbox snapshots change in the same transaction. Reconciliation derives balances from postings under a consistent snapshot and reports differences without editing history.

For this milestone, spending entitlement is one immutable `owner_subject` per ledger account. Customer account relationships, multiple owners, customer delegation from Payment, provisioning/restriction recovery, holds and partial refunds remain future milestones. The internal synthetic operator acts as its own verified subject. It cannot debit a different account owner except via a separately authorized full reversal. Do not expose the technical operator secret or the ledger route through the browser Gateway. Realm ADMIN/CUSTOMER roles grant no ledger privileges; separate `ledger-service` audience and client roles are required. The local operator deliberately has all technical roles for the isolated smoke journey; production service identities need narrower assignments.

This refines the initial conceptual insert-on-conflict outline in ADR 0003: identity advisory locks reduce contention/retry complexity, while database unique constraints, immutable outcomes and row locks remain authoritative. There is no Redis lock, distributed financial transaction or exactly-once messaging claim. Outbox publishing/delivery metadata belongs to Phase 5.

References: [PostgreSQL row locks](https://www.postgresql.org/docs/17/explicit-locking.html), [SECURITY DEFINER and safe search paths](https://www.postgresql.org/docs/17/sql-createfunction.html), [deferred constraint triggers](https://www.postgresql.org/docs/17/sql-createtrigger.html). These sources describe database mechanisms; FinCore's chart and policy choices are local design decisions.
