# ADR 0009: synchronous fraud authorization and investigation

Status: implemented; acceptance evidence is recorded in the Phase 6 report.

Fraud owns its database, migration/runtime roles, versioned policy, immutable assessments, initial alerts and investigation decisions. Payment submits only a durable payment ID. Fraud obtains the signed actor and immutable instruction identity from Payment, declared country from Customer and saved-beneficiary age from Beneficiary through narrowly scoped private clients. Public callers cannot supply risk counters or approval flags. Failed-payment counts are financial FAILED transitions in the preceding ten minutes, not failed logins. Country is a synthetic declared profile fact, not physical geolocation or sanctions screening.

One Fraud database transaction takes an actor advisory lock, admits the distinct payment and evaluates the observed counters. Same-payment replay consumes one slot. A fresh authorization renews a sixty-second velocity admission before evaluation; it cannot reuse an expired slot. The thirty-second assessment cache is bound to immutable identity, canonical context, rules version and investigation version. Independent currency thresholds use exact decimal amounts, without FX. Scores explain signals; only explicit strict blockers produce BLOCK. Multiple review signals cannot accidentally become an unreviewable hard block merely by adding scores.

Payment durably polls PENDING_RISK_REVIEW. An analyst approval is an audited decision, not settlement. Only the same rules and a subset of the reviewed signals can use that approval; new facts or rules require reassessment, and a strict blocker cannot be overridden. Rejection remains binding for that payment. Relaxation without analyst approval is explicitly CLEARED. Case updates use expected versions. A decision key retains the original request/response; unknown-response retries preserve the key, body and version. Replays can recover a stored decision without requiring Payment availability. Rules append immutable versions and use the expected version as their natural retry identity.

Ledger independently validates the opaque assessment ID against its own immutable instruction fingerprint and payment ID using a verification-only identity. The HTTP verification finishes before opening the posting transaction. The existing SQL posting-point expiry check and all financial constraints remain authoritative. Caller-supplied expiry alone cannot authorize execution. Already recorded Ledger outcomes are returned before consulting Fraud, allowing ambiguous requests to recover during an outage without duplicate posting. No dependency failure has an ALLOW fallback.

Initial REVIEW/BLOCK creates one immutable alert, case and outbox event in the assessment transaction. Subsequent assessments update the current case and append assessment history, without duplicating the initial alert. The immutable alert feed uses a stable descending sequence cursor. The case feed is a current work queue ordered by latest assessment; concurrent reassessment can move rows between pages, so it is not an archival snapshot. Notification consumes the alert asynchronously and creates an owned generic SECURITY notice; it does not announce successful payment or carry investigation details.

FRAUD_ANALYST is explicit at Gateway and Fraud. ADMIN alone has no investigation privilege; analyst access grants no funding, execution or reversal scope. The Payment worker can assess but cannot review. The Ledger risk client can validate but cannot assess or review. Fraud can read only minimal owner contexts and cannot write money. Existing private operator review delegates to the same audited Fraud decision, then returns the actual Payment state while the worker rechecks authorization.

The portal shows real cases, original alerts, explanations, decisions and the actual Payment/journal state when available. Confirmation is required for decisions and rule publication. Unknown responses retain the original intent for retry. No optimistic settlement is displayed.

This is a local synthetic-money system. Velocity admission is not a funds reservation. There is no distributed transaction across owner reads, no instant revocation of an already issued short-lived grant, no ML/sanctions claim, and no Kafka availability requirement for synchronous authorization. Cards and Ledger reservations remain Phase 7.
